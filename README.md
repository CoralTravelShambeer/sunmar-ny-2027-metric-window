# B2C landing

Проект лендинга для Coral или Sunmar. Сборка выполняется глобальным пакетом
`@coraltravelcenter/b2c-landing-builder`; Vite-конфигурация и исходники builder
в проект не копируются.

## Быстрый старт

Установите или обновите глобальный builder:

```bash
npm install --global @coraltravelcenter/b2c-landing-builder@latest
```

Запустите проект:

```bash
npm install
npm run check
npm run dev
```

`dev` поднимает Vite на `http://127.0.0.1:5173` и подключает лендинг к сайту
через Tampermonkey. Builder сам использует правильный домен бренда, URL
`/monkey/*` и контейнер `#monkey-app`.

## Команды

```bash
npm run check                 # проверить конфигурацию и файлы блоков
npm run dev                   # запустить режим разработки
npm run build                 # собрать CMS-файлы в @CMS/

npm run block:add -- hero     # добавить блок hero
npm run block:rename -- hero main-hero

npm run deploy:dry-run        # показать план без изменений в CMS
npm run deploy                # собрать и задеплоить checkout-версию
npm run deploy:section -- hero # задеплоить только секцию hero
npm run deploy:remote         # сохранить конфликтующие изменения из CMS
npm run deploy:force          # осознанно перезаписать remote локальной версией
npm run deploy:update         # изменить текущую CMS-версию на месте
npm run deploy:relink         # привязаться к существующей странице
npm run deploy:publish        # задеплоить и опубликовать страницу
npm run deploy:assets         # синхронизировать только ассеты
```

## Структура

```text
src/
  order.json
  markup/          # HTML или Pug по одному файлу на блок
  styles/          # CSS, SCSS или Less по одному файлу на блок
  scripts/         # необязательный JS или TS блока
    utils/         # общие JavaScript-утилиты для скриптов блоков
  components/      # компоненты Vue, если выбран Vue
public/             # изображения, шрифты и другие статические файлы
landing.config.mjs  # сайт, стек и минимальная версия builder
package.json
```

`src/order.json` управляет папкой на CDN и порядком блоков:

```json
{
  "folder": "project-name",
  "blocks": ["hero", "advantages", "footer"]
}
```

Итоговый адрес ассета:

```text
<assetsBase>/landing-pages/<order.folder>/<file>
```

Для каждого элемента `blocks` обязательны разметка и стили с тем же именем.
Скрипт необязателен. `check`, `dev` и `build` остановятся с понятной ошибкой,
если файл отсутствует или формат не соответствует `landing.config.mjs`.

## JavaScript и TypeScript

Скрипт блока экспортирует функцию инициализации по умолчанию:

```js
export default function hero() {
  const block = document.querySelector(".hero");
  if (!block) return;

  // Инициализация блока.
}
```

Builder сначала вставляет разметку, затем вызывает функцию без аргументов.
Контракт проверяется через AST, поэтому комментарий или строка с текстом
`export default` не считаются экспортом. Ошибки синтаксиса JS/TS также
обнаруживаются до запуска сборки.

Общие функции храните в `src/scripts/utils/` и импортируйте из скриптов блоков.

## Текст и Typograf

Русский текст в разметке автоматически типографируется при dev и build:
кавычки, тире, неразрывные пробелы и распространённые сокращения приводятся к
нормальному виду. Атрибуты HTML и содержимое `script`, `style`, `pre`, `code` и
`textarea` не изменяются.

## Изображения и CDN

Файлы размещаются в `public/` и подключаются от корня:

```html
<img src="/images/hero.png" alt="">
```

```css
.hero {
  background-image: url("/images/hero.png");
}
```

Перед deploy изображения JPG, JPEG и PNG автоматически преобразуются в WebP с
качеством 80. Исходники в `public/` не меняются, а ссылки в CMS-сборке
переписываются на `.webp`. Готовые WebP используются без повторной конвертации;
SVG, GIF, шрифты и остальные файлы копируются как есть.

CMS-файлы и служебный `manifest.json` создаются в `@CMS/`. Скрытые файлы вроде
`.gitkeep` в manifest и CDN не попадают.

Существующие CDN-файлы builder не перезаписывает из-за кеширования CMS. Если
содержимое картинки изменилось, дайте файлу новое имя и обновите ссылку.

## Deploy

Перед первым реальным deploy рекомендуется посмотреть план:

```bash
npm run deploy:dry-run
```

При первом `npm run deploy` builder авторизуется в Backoffice, предлагает
application, layout, HTML-зону и точную позицию, затем создаёт страницу. Пароль
не сохраняется; на диске кешируется только временный токен.

Повторный deploy использует состояние из `.b2c/deploy/`. Сохранённые
pageContentId и layoutAreaId сначала проверяются в CMS. Если страница, версия
или зона изменились, операция остановится до загрузки файлов — восстановите
привязку:

```bash
npm run deploy:relink
```

`relink` позволяет найти существующую страницу по названию или URL, выбрать её
версию, HTML-зону и позицию. Для предварительной проверки можно выполнить:

```bash
npm run deploy:relink -- --dry-run
```

Обычный deploy опубликованной страницы создаёт checkout-версию. Команда
`deploy:update` меняет выбранную версию на месте — используйте её осознанно.

После успешного deploy builder сохраняет снимок секций как `base` и при
следующем запуске сравнивает `local`, актуальный `remote` из CMS и этот `base`.
Независимые изменения секций объединяются автоматически. Если одна секция
изменена и локально, и в CMS, silent overwrite запрещён: интерактивный deploy
предложит сохранить remote, заменить его local или отменить операцию.

Для неинтерактивного разрешения конфликтов всей страницы используйте:

```bash
npm run deploy:remote  # оставить конфликтующие секции из CMS
npm run deploy:force   # принудительно применить local в scope всей страницы
```

Если достоверного base ещё нет, любое отличие local от remote считается
потенциальным конфликтом и также требует явного решения.

Чтобы заменить только один блок и сохранить остальные секции из актуальной
CMS-версии, передайте ключ блока из `src/order.json`:

```bash
npm run deploy:section -- hero
```

Если локальная и CMS-версии секции расходятся, builder предложит сохранить
remote или осознанно перезаписать её. Неинтерактивные варианты:

```bash
npm run deploy:section -- hero --remote
npm run deploy:section -- hero --force
```

Публикация выполняется отдельной командой:

```bash
npm run deploy:publish
```

Builder опубликует страницу только после успешной синхронизации виджетов и при
заполненных в Backoffice title, URL, SEO title и SEO description. Если
метаданных не хватает, публикация блокируется с перечнем полей.

## Удаление ассетов

Очистка отделена от обычного deploy. Сначала проверьте список:

```bash
npm run deploy:assets:prune -- --dry-run
```

Затем при необходимости выполните:

```bash
npm run deploy:assets:prune
```

Удаляются только отсутствующие в текущем `public/` файлы, которые этот builder
ранее сам загрузил и записал в deploy-state как управляемые. Файлы, уже
существовавшие в CMS до deploy, не удаляются.

## Безопасность deploy

- GET-запросы Backoffice имеют timeout и безопасные повторные попытки.
- Изменяющие запросы автоматически не повторяются, чтобы не создать дубли.
- Два локальных deploy одного проекта не могут выполняться одновременно.
- Если CMS-страница изменилась во время deploy, изменение виджетов отменяется.
- Соседние remote-секции никогда не заменяются при `deploy:section`.
- `--force` действует только в текущем scope: на страницу или выбранную секцию.
- `--dry-run` не загружает файлы, не меняет CMS и не записывает deploy-state.

После успешного deploy терминал показывает количество добавленных, обновлённых
и удалённых виджетов, состояние ассетов, preview-ссылку и live-ссылку после
публикации.
